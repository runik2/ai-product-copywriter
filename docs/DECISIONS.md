# Решения

## Промпты: v1 → v2

**v1 (первый вариант).** Промпт просил «написать SEO-текст до 800 символов» и подчёркивал
пользу для B2B. На практике это провоцировало три класса ошибок: добивание объёма общими
фразами, добавление цены/наличия/гарантии из «здравого смысла» и упоминание характеристик,
которых нет во входных данных. В публичном тексте появлялись служебные формулировки вроде
«в исходных данных указано».

**v2 (текущий).** Версия лежит в `prompts/system_ru.md`, а её идентификатор — в
`validation.prompt_version`, не в списке `warnings`.

Что изменено и почему:

- вход объявлен недоверенным JSON; инструкции из описания товара не исполняются;
- разрешены только факты из JSON, запрещены знания «по аналогии», расшифровка кодов модели,
  сертификаты, нормативы, материалы, габариты, цена, наличие, сроки, гарантия, совместимость;
- запрещено называть характеристики из `missing_fields`;
- публичные `seo_title`/`seo_description` не должны содержать служебных фраз; пояснения
  о пробелах разрешены только в `manager_notes`;
- если фактов меньше чем на 800 символов, нужно вернуть честный короткий текст, а не
  добивать объём;
- зафиксирован точный JSON-контракт и ограничение заголовка 70 символами.

Почему версия не warning: это метаданные результата, а не дефект текста. Список
`warnings` должен содержать только действия, которые нужно исправить или проверить.

## Генерация

- До трёх попыток. Пустые `warnings` завершают цикл досрочно; иначе возвращается попытка
  с минимальным числом предупреждений (при равенстве — более ранняя).
- В следующую попытку передаются предупреждения предыдущей лучшей попытки, чтобы модель
  исправляла конкретные числа/утверждения, а не переписывала всё вслепую.
- `prompt_version` всегда `v2`; `llm_skipped` появляется только когда во входе нет ни
  `specs`, ни `description`, и API не вызывается.
- Невалидная карточка от модели — `ResultError` (код 5), а не ошибка входа.

## LLM и коды возврата

- 400/401/403 не повторяются и дают разные сообщения: неверный ключ, неверная
  модель/endpoint, нет доступа к сети/прокси или модели.
- Повторяются только 429, 5xx и таймауты/сетевые обрывы, с паузой 1 с, затем 2 с.
- 404 трактуется как неверный endpoint и тоже не повторяется.
- Невалидный JSON/конверт ответа — код 5; сеть/API — 4; конфигурация — 3; вход — 2.
- `generate` обрабатывает каждый товар отдельно: ошибка одного не мешает сохранить
  остальные, итоговый код — худший. Ошибки печатаются в stderr, статус — по каждому товару.

## Проверки

- «Цен» ловится только как слово про цену: `цена`, `цены`, `цене`, `цену`, `ценой`,
  `ценами`, `ценах`, `ценник*`, `ценов*`. «Центральная», «ценный», «оценка» и «бесценный»
  не срабатывают.
- Единица «в» не считается технической: иначе «5 В» давало бы ложную пару. Для вольт
  остаётся только проверка числа.
- `%` и `℃` разбираются отдельно, без `\b` после символа; `℃` и `°C` приводятся к одной
  канонической паре. Чужие `1.5` и `60 °C` при исходных `1,6 МПа` и `20 °C` ловятся.
- Предупреждения о длине описания не блокируют `check`: публикация короткого честного
  текста допустима, если в `missing_data` видно, чего не хватает.

## Обогащение из JSON-LD

- Источник: публичная страница товара, указанная в `url` оффера. Для первого товара —
  `https://www.souz-pribor.ru/product/testo-mini-termometr-poverkhnostnyy/`, дата снимка
  **2026-11-09**.
- Исходный JSON-LD (`@type: Product`) сохранён в
  `examples/inputs/raw/product_1.page.json` без HTML-дампа страницы.
- Добавлено: `Верхний предел измерений`, `Нижний предел измерений`, `Измерение влажности`,
  `Память`, `Диапазон измерений` (из текста `-50 … +300 °C`), расширенное описание с
  наконечником, дисплеем и индикатором батареи.
- Удалено: рекламная фраза «Привлекательная цена», служебное поле «Популярные подборки»
  и другие нетехнические поля (категория, наличие, доставка, рейтинг, отзывы, скидки).
- Текст JSON-LD очищается с разделителями на границах тегов, строк и склеенных слов:
  `термометрПривлекательная` → `термометр. Привлекательная`, а затем рекламная фраза
  вырезается. Без этого слова слипались и попадали в промпт как один токен.
- Обогащение — явный флаг `feed pick --enrich`; он применяется к каждому выбранному
  товару, а не к `chosen[0]`. Исходный JSON-LD каждого обогащённого товара сохраняется
  рядом с XML-фрагментом.
- Ограничение: страница второго товара (`/product/tsp-k/`) — групповая карточка серии.
  Её свойства описывают серию, а не конкретный вариант; `missing_data` всё равно требует
  диапазон и тип чувствительного элемента. Для максимально строгого разбора запускайте
  `feed pick` без `--enrich`.

## Данные и воспроизводимость

- Полный YML не коммитится (`data/` в `.gitignore`); в репозитории только компактная
  тестовая фикстура и сохранённые фрагменты выбранных офферов.
- `examples/outputs` — результат реального прогона обоих товаров текущим кодом и текущим
  промптом. Повторный прогон может отличаться формулировками из-за недетерминированности
  LLM, но проверки и структура воспроизводимы.
- Ключ хранится только в локальном `.env`; `.env` в `.gitignore`, в отчётах и коммитах
  его нет.

## Ограничения

- Нет CMS, БД, деплоя, кэша и массовой обработки.
- Качество ограничено полнотой фида и страницы; 800 символов — ориентир, а не цель любой
  ценой.
- Нет автоматической сверки JSON-LD с конкретным вариантом товара; групповые страницы
  требуют ручного внимания.
- Нет эталонного набора качества и A/B-оценки SEO; проверки ловят фактические ошибки,
  но не стилистику.
- Один провайдер и один формат ответа; смена модели может потребовать правки промпта.

## Возможные улучшения

Кэширование ответов, пакетная обработка, эталонный набор карточек, сравнение моделей,
human-in-the-loop редактор, справочник допустимых единиц и полей, проверка JSON-LD по
SKU/артикулу, экспорт в CMS, structlog и метрики качества.
